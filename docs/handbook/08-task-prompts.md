# Copyable Task Prompts

These prompts are for a teammate to give their development assistant. Replace task/issue placeholders and provide authorized workspace access. They do not create account access, authorize third-party messages, or enable unattended work by themselves.

## 1. Backend and funding rules

> Read AGENTS.md, START_HERE.md and handbook chapters 01, 02, 04 and 05. Inspect the repository and work on issue [ID]. Implement the smallest case-review backend increment using the existing stack if present. Keep unknown amounts null. Preserve units, dates, case linkage, funding overlap and source provenance. First implement deterministic funding tests for separate/included/unknown grants, duplicate items, mixed currency, stale figures and missing costs. Do not start paid inference for arithmetic. Add actual tested setup commands; do not pretend proposed endpoints already exist. Report changed files, tests, mode and next action. Escalate only product-boundary or access decisions.

## 2. Frontend and design

> Read AGENTS.md, START_HERE.md and handbook chapters 01, 02, 03 and 05. Build a warm, accessible case-first interface using the shared response contract. Start with explicitly synthetic fixtures if the backend is not ready. Include source inspection, funding uncertainty, follow-up questions and secondary later updates. Do not create a trust score or certify a charity. Clearly mark fixture-backed behavior. Test a 390px mobile viewport, keyboard interactions, missing-data states and failed-provider state. An available design skill may help, but inspect its result. Open a small PR with screenshots and interactions actually tested.

## 3. Evidence research

> Read handbook chapters 01 and 02. Find a permitted case bundle for one cat medical fundraiser in Toronto or Ontario. Record organization/case identifiers, dated treatment request or cost estimate, funding statements, original URLs, origin groups, capture dates, source periods and what each source cannot establish. Do not bypass social media restrictions, contact anyone or upload private documents without authorization. Do not equate a registered charity with an authenticated appeal. If suitable real evidence is unavailable, report the exact missing inputs and prepare a clearly synthetic fixture for engineering, not a fictional real rescue story.

## 4. H-MEM integration

> Read our handbook's H-MEM requirements and the official upstream H-MEM instructions. Inspect the current implementation before installing anything. Integrate memory into a real case function: preserve sourced case facts, recall them after restart and consume them in a follow-up answer or comparison. Keep user/case scope and source lineage. Demonstrate a correction and a different alias not recalling the same state. Run relevant reference conformance and application checks. Do not claim Nightshift works because H-MEM works, and do not turn memory confidence into a charity score.

## 5. NVIDIA or Nightshift provider adapter

> Read handbook chapter 04 and the chosen provider's current official contract. Work on only the selected adapter and issue [ID]. Use backend-held credentials, explicit provider selection, bounded calls and sanitized errors. For Nightshift, verify /v1/models with a real token and distinguish unauthorized from offline. Confirm the runtime is reachable from the backend machine. Make one useful public/synthetic evidence call only with the available authorized account, then record actual outcome, returned model and usage. No fake success, silent provider fallback, paid upgrades, network exposure or large model downloads. If blocked, document the smallest reproducible failure and continue with mocked adapter tests labelled as tests.

## 6. Review and demonstration

> Read the product boundaries and Delivery acceptance table. Inspect the branch as a reviewer unfamiliar with the chat history. Exercise the main case journey and unknown/error states; map each finding back to its actual source; check funding inclusion and timestamps. Verify claimed external calls and H-MEM use from recorded evidence. Separate fixture, historical and live behavior. Run actual setup from a clean checkout where feasible. Report failing gates rather than silently lowering the definition of done. Prepare a short demo script and a restartable handoff.

## 7. Blocked-task handoff

> Stop changing unrelated components. Identify the failing stage, last working commit, sanitized reproduction, what was already tried and the exact next action. Use the problem-routing table. If a product decision is truly needed, offer two concrete options and a recommendation for Shiyuan; otherwise route to the technical/account owner. Continue an independent authorized task. No reply is not approval.
