HOW THE BACKEND WORKS

Evidence first.
Clear limits at every step.

We help supporters understand a rescue’s need, and help organizations see what public information is missing. Below is what runs today—not a claim that every planned integration is complete.

1 · The product experience

Supporter

“I want to help a cat. What evidence supports this appeal? How much is still needed?”

Today: one curated real lead, Lucy. Missing funding figures remain unknown; the case stays pending.

Rescue organization

“What should we publish so supporters can understand and check our appeal?”

Today: a fictional five-step walkthrough, plus a separate saved-research Lucy checklist.

Next development step: one chat entry that recognizes supporter, organization or both intents, asks briefly when unclear, and allows switching. The separate screens currently illustrate the journeys. A stated role does not prove authority to represent an organization.

2 · One real investigation, with feedback

These are conditional software roles, not six independent language-model calls. They execute sequentially to keep compute small, but the review can branch and feed back.

EVALUATOR ↔ RESOLVER ↔ COORDINATOR

A conflict changes the action

Lucy example: one article reports pregnancy; a later article reports birth. The evaluator requests a chronology check. The resolver checks dated, sourced statements; the coordinator revises the account only if supported. Otherwise the conflict stays unresolved.

Feedback loop: evaluator → focused resolution → revised account → evaluate again. Changed sources or previous gaps alter which checks run. No endless retry or extra paid call.

real_review.py · source_analysis.py
↓ stop when evidence or budget is insufficient
H-MEM + STRUCTURED RESPONSE

Store the review; show what is known and missing

Save source references, quotes, fingerprints and unresolved gaps in the case’s memory. The next explicit review can recall them. Lucy remains pending, with remaining amount unknown. Tool failures remain explicit.

Internal role traces are available through the local debug view; ordinary users see the evidence and result rather than raw backend traces.

The separate fictional fixture demonstrates a targeted funding repair: clarify whether a grant overlaps with the reported donations → re-evaluate → calculate the disclosed gap. Fictional facts never qualify a real case.

3 · Which tool works at which layer?

CONNECTED WHEN CONFIGURED

Meterless H-MEM

Runtime memory. Official local reference saves, recalls and retains sourced case reviews. Requires Node 24 and an explicit reference path; otherwise memory is unavailable.

It does not independently verify evidence or supply a language model.

ONE SEPARATE LIVE TEST

NVIDIA

Model inference / extraction. One authorized text extraction on simulated material succeeded (281 tokens), with validated replay.

Normal demo interactions do not call NVIDIA. The current real article extraction uses narrow code rules. Further live calls need a configured budget.

SEPARATE QUERY TEST

Zetaris

Connected structured data. A read-only query returned historical Toronto Cat Rescue identity data.

Lucy’s runtime review is not wired through Zetaris. That historical result does not verify Lucy, current medical need or current risk. Source collection still needs authorized readers/connectors.

DEFERRED / NOT CONNECTED

Meterless Nightshift

Planned model routing. Intended to route calls to configured providers.

No working application connection is established. A web-tab setup is not proof of an endpoint reachable by Python. H-MEM alone does not establish compliance with the separately stated Nightshift requirement.

DEVELOPMENT LAYER

Codex / Cursor / Claude Code

Tools used by developers to build, debug, test and document the product. This increment was built and checked with Codex; coding assistants are not running as hidden product services.

Josh’s logo/home design is adapted into the working local interface.

APPLICATION LAYER

Python + browser

Local server, policy checks, bounded role orchestration, source reading, deterministic extraction, arithmetic and presentation. No GPU required for these parts.

The organization walkthrough is browser-only, entirely simulated and makes no API/model calls.

4 · What we can honestly demonstrate

  • Real path: curated Lucy lead → explicit two-article refresh → sourced observations → conditional chronology resolution → H-MEM save/history when configured → pending result.
  • Fictional path: missing funding detail → targeted repair → updated calculation and retained history.
  • Organization walkthrough: public URL → gaps and publication advice → simulated website update → recheck → supporter preview, still pending independent checks.

Current limits

  • One real lead, not general web discovery. No arbitrary social posts, video analysis or document upload.
  • No general chat model. Intent handling is bounded and can ask for clarification; unified dual-role chat is next.
  • No qualified real recommendation: clinical, current funding, treatment location, recipient and risk evidence are incomplete.
  • Latest article reading does not refresh saved manual government/donation-form observations. History is not a fresh check.
  • Local prototype only: no production authentication, multi-user concurrency, durable feedback queue or hosted service.
  • No payments, private evidence intake, automatic outreach, or tracing an individual donor’s money.
  • Limited-credit demo: reuse facts, cap calls/time/tokens, no automatic paid retries. Additional credit could fund broader permitted evidence and model support; it cannot replace verification.
